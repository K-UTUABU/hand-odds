# 0004 シミュレーションの方法と実行場所

## 背景

厳密な計算とは別の方法で求めた値を並べ、計算の正しさの証拠にする（設計書 3.3）。
10万回の実行時間によっては、画面が固まらないよう Web Worker に移す必要がある。

## 決めたこと

- デッキを「グループ番号の配列」で表し（その他は `groups.length`）、毎回先頭 `handSize` 枚だけを入れ替えで選ぶ（Fisher–Yates の途中まで）
- 乱数は種つきの mulberry32。`Math.random` は使わない
- 成立の判定は`matches` を使う（条件の解釈をシミュレーション側で二重に実装しない）
- 誤差の範囲は標準誤差の3倍（`margin`）。基準には厳密な値を使う
- 配列と枚数のバッファは使い回し、試行ごとに確保しない
- 実行場所：上限いっぱいの入力（デッキ100・引く10枚・10グループ各9枚・6パターン）で、10万回1回あたり約 120〜140 ミリ秒（4回測定：140, 134, 124, 122。vitest 上、Windows 11）。
  300 ミリ秒以内なので、**画面と同じ場所（メインスレッド）で動かす**。Web Worker は使わない。
  ただしこの測定は Windows のデスクトップ上の Node（vitest）で行ったもので、スマートフォンでは数倍遅い可能性がある。結果の表のタスクで実機の画面で測り直し、入力やボタンの操作が引っかかるようなら Web Worker に移す

## 理由

- 途中までの Fisher–Yates は、試行ごとに配列を戻さなくても、並び順がどうであれ次の先頭 `handSize` 枚は一様な無作為抽出になる
- 種を固定できるので、テストが毎回同じ結果になり再現できる
- シミュレーションは条件の基準となる解釈である `matches` を使い、`exact` は速さのために事前に作った最小・最大の配列で独自に判定する。2つは別々に書かれているので、食い違えば突き合わせのテストで見つかる（`exact.test.ts` の 70 通りの手札の総当たりのテストも、両者を結びつけている）

## 捨てた案

- `Math.random`：種を指定できず、テストを再現できない
- 毎回デッキ全体を混ぜる：必要なのは先頭 `handSize` 枚だけで、無駄
- Web Worker：測定結果が基準内なので、構成が複雑になるだけ
