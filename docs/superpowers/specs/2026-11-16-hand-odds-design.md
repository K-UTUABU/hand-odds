# 初手の確率計算ツール 設計書

- 作成日：2026-11-16
- 状態：承認済み（2026-11-16）
- 仮の名前：hand-odds（リポジトリ名・画面の表題は依頼者が変更できる）

この文書で「依頼者」はリポジトリの持ち主（人）、「作り手」は実装を任される AI（Claude Code）を指す。
「依頼者が決めた」と書いていない項目は、作り手の提案であり、依頼者が後から変えられる。

---

## 1. 意図

転職用ポートフォリオのサブ作品。メイン（家計簿アプリ）は、依頼者が自分で理解して書くことで技術理解を示す。
このサブ作品は逆に、**実装とテストをすべて AI に任せ**、依頼者は要件定義と受け入れ判定だけを行う。

見せたいのは次の力（依頼者が決めた）：

- 作業を指示し、任せる力（マネジメントの素養）
- 成果物から「何をどうしたのか」を読み取り、合否を判定する力

そのため、アプリそのものと同じ重みで、**任せた過程がリポジトリから読み取れること**を成果物とする。

題材にカードゲームの確率を選んだ理由：依頼者の得意分野で、答えを手計算で検算できる。
コードを全部読まなくても、受け入れ基準を書いて合否を言える。

## 2. 目標・対象外・失敗とみなすもの

### 目標

- デッキをグループに分けて枚数を入れると、初手で条件を満たす確率が分かる
- 厳密な計算とシミュレーションの両方で求め、並べて見せる
- URL 1つで誰でも触れる（採用担当がインストールなしで試せる）
- 要件 → 受け入れ基準 → 作業 → 自動チェック → 判定、の跡が GitHub 上に残る

### 対象外（依頼者が決めた）

- カードごとのデータ（名前・効果・画像）。特定のゲームの情報は持たない
- 引き直し（マリガン）、ターンが進んだあとのドロー、サーチやドロー効果
- ログイン、サーバー、DB

### 対象外（作り手の提案）

- 入力内容の保存・共有（再読み込みで消えてよい）。後から足す候補として README に書く
- 先攻・後攻の専用機能（引く枚数を変えれば表せる）
- 日本語以外の表示

### 失敗とみなすもの

- 確率が間違っている（見た目が良くても失敗）
- 依頼者が1日で読み切れない量になる。目安（作り手の提案）：テストを除くコードは合計 800 行以内、
  プルリクエストは 10 件以内、1件の差分は 300 行以内（自動生成されるファイルを除く）。
  読む対象は、プルリクエストの説明と差分、判断の記録、README
- どう任せてどう確かめたかが、リポジトリから読み取れない
- 依頼者の許可なく、受け入れ基準（検算表）が書き換わる

## 3. 作るもの

### 3.1 用語

| 用語 | 意味 |
|---|---|
| デッキ枚数 | デッキの総数 |
| 引く枚数 | 初手の枚数 |
| グループ | 使う人が決めるカードの分類（例：初動、妨害、事故札）。名前と枚数を持つ |
| その他 | どのグループにも入れなかった残り。自動で計算され、条件は付けられない |
| パターン | グループごとの「◯枚以上・◯枚以下」をまとめたもの。すべて満たすと成立 |

決まりごと（依頼者が決めた）：

- 1枚のカードは1つのグループにだけ属する
- パターンは複数登録できる
- 出す確率は、パターンごとの成立確率と、**どれか1つでも成立する確率**

### 3.2 入力と制限（制限値は作り手の提案）

| 項目 | 範囲 | 初期値 |
|---|---|---|
| デッキ枚数 | 1〜100 | 40 |
| 引く枚数 | 1〜デッキ枚数、かつ 10 以下 | 5 |
| グループ数 | 1〜10（依頼者が決めた） | 1 |
| グループの枚数 | 0 以上。合計はデッキ枚数以下 | 0 |
| パターン数 | 1〜6 | 1 |
| 条件（グループごと） | 最小 0 以上、最大は空欄なら上限なし。最小 ≦ 最大 | 最小 0、最大なし |

引く枚数の上限を 10 にした理由（作り手の提案）：厳密な計算は枚数の組み合わせをすべて列挙する。
グループ 10 個・引く枚数 20 枚だと約 3,000 万通りになり、入力のたびにすぐ更新できない。
引く枚数 10 枚なら最大でも約 18 万通りで、一瞬で終わる。対象は初手だけなので、10 枚あれば足りる。

入力の誤り（合計がデッキ枚数を超える、最小が最大より大きい、など）は、その項目の近くに日本語で示し、
確率は表示しない。条件が成立しえない場合（例：4枚しかないグループに 5枚以上）は誤りではなく、0% と表示する。

### 3.3 計算

**厳密な計算**

- 多変量の超幾何分布を使う。初手に含まれる各グループの枚数の組み合わせ（その他を含む）をすべて列挙し、
  それぞれの確率を求める
- パターンの成立確率は、そのパターンを満たす組み合わせの確率の合計
- 「どれか1つでも成立」は、**いずれかのパターンを満たす組み合わせの確率の合計**として求める。
  パターンごとの確率を足し合わせてはいけない（重なりを二重に数えるため）
- 組み合わせの数は整数で正確に計算し（桁あふれしない方法で）、最後に割り算する。
  3.2 の制限いっぱいの入力でも、誤差は 10 のマイナス 9 乗未満とする

**シミュレーション**

- デッキを実際に混ぜて引く操作を繰り返し、成立した割合を出す
- 回数の初期値は 10万回。乱数は種を指定でき、同じ種なら同じ結果になる（テストで再現するため）
- 画面では「もう一度実行」で種を変えてやり直せる

**2つを並べる理由**：別々の方法で求めた値が合うことが、計算の正しさの証拠になる。
依頼者が検算していない入力でも、食い違いがあれば分かる。

### 3.4 画面

1画面のみ。スマートフォンの幅でも横にはみ出さずに使える。入力を変えると、厳密な計算の結果はすぐに更新される。

```
初手の確率計算

デッキ [40] 枚    引く枚数 [5] 枚

グループ                         [+ グループを追加]
  初動     [9] 枚   [削除]
  妨害     [6] 枚   [削除]
  事故札   [4] 枚   [削除]
  その他   21 枚（自動）

パターン                         [+ パターンを追加]
  パターン1「理想の初手」                    [削除]
    初動   [1] 枚以上 [ ] 枚以下
    妨害   [1] 枚以上 [ ] 枚以下
    事故札 [0] 枚以上 [0] 枚以下
  パターン2「最低限」                        [削除]
    初動   [1] 枚以上 [ ] 枚以下
    妨害   [0] 枚以上 [ ] 枚以下
    事故札 [0] 枚以上 [ ] 枚以下

結果                    厳密な計算   シミュレーション（10万回）
  パターン1「理想の初手」   xx.xx%      xx.xx% ±0.xx  誤差の範囲内
  パターン2「最低限」       xx.xx%      xx.xx% ±0.xx  誤差の範囲内
  どれか1つでも成立         xx.xx%      xx.xx% ±0.xx  誤差の範囲内
                                 [シミュレーションを実行]
```

- 各パターンには、**すべてのグループの行を常に並べる**。初期値の「0枚以上・上限なし」は条件なしと同じ意味。
  グループを追加すると、全パターンに条件なしの行が増える
- シミュレーションは**ボタンを押したときだけ**走る。回数は 10万回で固定し、画面からは変えられない。
  押すたびに種が変わる。入力を変えたら、古いシミュレーションの結果は消す（厳密な計算だけが残る）
- シミュレーションの値には誤差の目安（標準誤差の3倍、百分率）を添え、厳密な値との差がその範囲に
  収まっていれば「誤差の範囲内」、外れていれば目立つ警告を出す。
  10万回では小数第2位まで一致しないのが普通なので、数字を並べるだけでは「合っていない」と誤解されるため
- 確率は百分率で小数第2位まで
- グループ名・パターン名は自由に入力でき、空なら「グループ1」「パターン1」のように自動で付く
- グループを削除すると、各パターンからそのグループの条件も消える

## 4. 作り方の案と、選んだもの

| 案 | 中身 | 良い点 | 弱い点 |
|---|---|---|---|
| **1. 静的サイト（採用）** | 計算は画面に依存しない TypeScript の関数、画面は React。GitHub Pages で公開 | サーバーも DB も不要で最も軽い。URL 1つで触れる。家計簿のフロントと同じ構成で、依頼者が読みやすい | Java が出てこない |
| 2. Spring Boot の API + 画面 | 計算を Java の API にする | 依頼者の得意な Java で読める | 家計簿と構成が重なる。公開にサーバーが要る |
| 3. Java のコマンドラインツール | 画面なし | 最小 | 採用担当が触れない |

依頼者が案1を選んだ。理由：Java は家計簿で示せており、サブは軽さと「触れること」を優先する。

進め方の案としては「GitHub を使わずローカルだけで進める」もあったが、任せた過程が外から見えず、意図に合わないので外した。

### 技術構成（作り手の提案。家計簿のフロントに合わせる）

- Vite + React + TypeScript、Tailwind CSS
- テスト：Vitest + React Testing Library
- リント：oxlint
- 自動チェックと公開：GitHub Actions、GitHub Pages
- 計算（厳密・シミュレーション）は React を import しない純粋な関数として分け、単体でテストする

バージョンは実装時点の安定版を、公式の情報で確認して決める。

## 5. 任せ方の仕組み（ハーネス）

### 5.1 役割（依頼者が決めた）

| だれ | やること |
|---|---|
| 依頼者 | 要件定義、検算表の作成、プルリクエストの取り込み・差し戻しの判定、認証が要る操作（GitHub のログイン、リポジトリ作成、公開設定） |
| 作り手 | 実装、テスト、文書、プルリクエストの作成 |

### 5.2 決まり

1. **検算表は依頼者のもの**
   `docs/acceptance/kensan.md` に、依頼者が手計算で確かめた「入力と正解」を置く。
   作り手はこれをそのままテストにする。作り手は検算表と、それを写したテストの期待値を、依頼者の許可なく変えない。
   テストが通らないときは、実装を直すか、検算表の誤りの疑いを根拠つきで依頼者に報告する。
   書式は作り手がひな形（表）を用意する。列は、番号／デッキ枚数／引く枚数／グループと枚数／パターンの条件／
   正解／計算の式。正解は 0〜1 の小数で**小数第6位まで**書く（例：0.754321）。分数を併記してもよい。
   テストは、厳密な計算の結果との差が 0.000001 未満なら一致とみなす。
2. **検算は公開の前、計算の値を見せる前に**（2026-11-17 に依頼者の提案で変更。元は「検算表が先、実装が後」）
   計算の実装は、検算表を待たずに進めてよい。ただし、依頼者が検算表を記入し終えるまで、
   作り手は計算の結果の数値を依頼者に見せない（先に見ると、手計算が答え合わせに引っ張られるため）。
   検算表の全件がテストで通るまで、公開しない。経緯は `docs/decisions/0002-acceptance-order.md`。
3. **課題 → プルリクエスト → 自動チェック → 依頼者の判定**
   作業は GitHub の課題に分ける。作り手は課題1件につきブランチ1本とプルリクエスト1件を作る。
   作り手は main に直接入れず、自分で取り込まない。取り込むのは依頼者だけ。
4. **自動チェック**
   プルリクエストごとに、型チェック・リント・テスト・ビルドを走らせる。通らないものは取り込めない設定にする。
5. **プルリクエストの書き方**
   決まった型を使う：何をしたか／なぜ／どう確かめたか（実行した結果）／自分で決めたこと／特に見てほしい点。
   依頼者が全部のコードを読まなくても、判定の手がかりが得られるようにする。
6. **判断の記録**
   作り手が自分で決めた、後から変えにくいこと（計算の方法、制限値、ライブラリの選択など）は、
   `docs/decisions/` に1件1ファイルで、理由と捨てた案をつけて残す。
7. **突き合わせのテスト**
   種を固定したシミュレーションと厳密な計算が、統計的な誤差の範囲で一致することを、複数の入力で確かめる。
   あわせて、全組み合わせの確率の合計が 1 になることを確かめる。
8. **作り手向けの決まりの置き場所**
   上の 1〜7 をリポジトリの `CLAUDE.md` に書き、作り手が毎回読む。
   家計簿側の決まり（削除と認証は事前に確認、返答は日本語）もそのまま適用する。

### 5.3 立ち上げの手順と、GitHub の操作の分担

- リポジトリは**公開**にする（ポートフォリオとして見せるため。無料プランでは、公開でないと
  取り込みの制限と GitHub Pages が使えない）
- 依頼者が行う：GitHub へのログイン（`gh auth login`）、リポジトリの作成、
  main の保護（自動チェックの通過を必須にする）と Pages の公開設定。作り手は手順を文章で用意する
- 最初の1回だけの例外：設計書・`CLAUDE.md`・ひな形・自動チェックの設定は、依頼者の許可を得て
  main に直接入れる（空の main にはプルリクエストを出せないため）。そのあとで main を保護し、
  以降はすべてプルリクエストを通す
- 作り手が行う：課題の作成、作業用ブランチの push、プルリクエストの作成。
  このリポジトリに限り、都度の確認なしで行ってよい（依頼者が決めた、2026-11-16）。
  main への push、強制 push、ブランチやファイルの削除、認証情報の操作は、この許可に含まれない

### 5.4 検算表に入れてもらう例（最低5件、作り手の提案）

依頼者が数字を決め、正解を計算する。次の種類を1件ずつ含める。

1. 1つのグループを 1枚以上引く
2. 1つのグループを 1枚も引かない
3. 2つのグループをどちらも 1枚以上引く（引きたいカードと引きたくないカードを一緒に引く）
4. 3つのグループをすべて 1枚以上引く（A・B・C がそろう）
5. 2つのパターンのどちらかが成立する（A と B、または A と C）

### 5.5 README に書くこと

概要、公開 URL、使用技術、起動方法に加えて、「この作品の作り方」の節を設ける。
役割分担、検算表、課題とプルリクエストの流れを説明し、実際の課題・プルリクエスト・判断の記録へリンクする。
採用担当がここから過程をたどれるようにする。

## 6. 制約

- 特定のゲームの名前・カード名・画像・ロゴを、アプリにも README にも使わない
- リポジトリは家計簿とは別（ローカルは `D:\hand-odds`）
- コミットの作成者は、家計簿と同じ設定（GitHub の noreply アドレス）を使う。個人のメールアドレスは入れない
- 外部のサービスへ入力内容を送らない（計算はすべてブラウザの中）

## 7. 作り手に任せること

- 課題への分け方と順番（ただし「検算は公開の前、計算の値を見せる前に」「自動チェックの整備は早い段階で」を守る）
- ファイルとコンポーネントの分け方、状態の持ち方
- シミュレーションを画面の裏側（Web Worker）で動かすかどうか。入力中に画面が固まらないことが条件
- 乱数の方式、組み合わせの数を正確に計算する方法
- 見た目の細部（色、余白、部品）。3.4 の構成と、スマートフォンで使えることを守る
- GitHub Actions と Pages の具体的な設定

## 8. 完成の条件

- 検算表の全件がテストで通る
- 突き合わせのテストと、確率の合計のテストが通る
- 入力の誤りと、成立しえない条件の表示が 3.2 のとおり
- 公開 URL で、スマートフォンとパソコンの両方から使える
- README から、課題・プルリクエスト・判断の記録をたどれる
- 依頼者がすべてのプルリクエストを判定し、取り込んでいる
